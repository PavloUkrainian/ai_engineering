# AI Engineering: Наскрізний проєкт (DocAI / KYC / FinTech Compliance)

Цей репозиторій містить рішення практичних кейсів наскрізного курсового проєкту курсу **AI Engineering (2 потік)**:
* **Кейс 1:** Вилучення структурованих даних із зашумлених OCR-текстів документів (Pydantic, Few-Shot, Self-Correction, Benchmark моделей).
* **Кейс 2:** Повний зріз RAG-системи на нормативному корпусі DocAI / KYC: від сирих документів (PDF/MD/HTML) до відповідей з джерелами та CI Evals.

**Оптичне розпізнавання, верифікація документів та комплаєнс-асистент (DocAI / Identity Verification / KYC / AML)**.

1. **Кейс 1 (Data Extraction):** Обробка сильно зашумлених мобільних OCR-сканів документів, що посвідчують особу (паспорти 1994 року, ID-картки, біометричні закордонні паспорти, водійські посвідчення).

## ✂️ Обґрунтування стратегії чанкінгу (Structure-Aware vs Fixed-Size)

Для регуляторних стандартів та технічних регламентів наївний чанкінг фіксованої довжини (Fixed-Size Window) призводить до критичних втрат контексту:
- Розриває речення та математичні формули розрахунку контрольних сум на середині слова чи числа;
- Втрачає прив'язку до статті / розділу закону (модель не розуміє, чи йдеться про паспорт TD3, чи про водійське посвідчення);
- Знижує точність цитування джерел на кроках RAG.

### Обрана стратегія: Structure-Aware (Semantic / Section-based) Chunking
1. **Збереження логічної ієрархії:** Текст нарізається за природними межами розділів, статей та підзаголовків (`##`, `<h3>`, нумеровані пункти).
2. **Контекстний префікс:** До кожного чанка додається заголовок `[Назва Документа > Назва Розділу]`, завдяки чому векторний пошук та Cross-Encoder завжди мають повний семантичний контекст.
3. **Цільовий розмір:** 150–400 токенів із перекриттям (overlap) 50 токенів для великих розділів. Це оптимальний розмір для моделей ембеддінгів (`text-embedding-3-small`, `all-MiniLM-L6-v2`) та контекстного вікна генерації.
4. **Повні метадані:** Кожен чанк має унікальний `chunk_id`, `doc_id`, `source_file`, `doc_title`, `section_title`, `doc_type`, `version_date`, `doc_hash`, `chunk_hash`, `token_count`.

### Емпіричне порівняння на корпусі документів

| Метрика | Structure-Aware (Наша) | Fixed-Size (500 chars) | Чому це важливо |
| :--- | :---: | :---: | :--- |
| **Всього згенеровано чанків** | **78** | 74 | Оптимальна гранулярність без надлишкової фрагментації |
| **Середня кількість токенів** | **104.2** | 96.2 | Збалансований розмір для семантичного пошуку |
| **Діапазон токенів (min - max)**| **22 - 174** | 12 - 125 | Відсутність мікро-уламків без змісту |
| **Збереження меж речень (Integrity)**| **93.6%** | **48.6%** | У Fixed-Size понад 51% чанків обриваються посеред речення |
| **Наявність контексту розділу** | **100.0%** | **0.0%** | Критично для точного цитування джерел у RAG |

Результати вивантажено у `data/manifest.json`, `data/chunks.jsonl` та `results/chunking_comparison.json`.

## 🔍 Індекс та Hybrid Search (Крок 2)

Для забезпечення максимальної точності знаходження потрібного нормативного пункту реалізовано повноцінний гібридний рушій пошуку:
1. **Векторний індекс (Qdrant in-memory / local):**
   * Ембеддінги: `text-embedding-3-small` (1536 вимірів) з дисковим кешуванням у `data/embeddings_cache.json` та детермінованим fallback для CI.
   * Колекція `kyc_docai_chunks` з метрикою `Cosine Distance` та збереженням повного payload.
2. **Лексичний індекс (BM25Okapi):**
   * Токенізація термів для кирилиці та латиниці зі збереженням критичних абревіатур (ICAO, TD1, TD3, MRZ, DPI, РНОКПП, FATF, PEP, OVI).
3. **Гібридне злиття (Reciprocal Rank Fusion - RRF):**
   $$\text{RRF}(d) = \sum_{m \in \{\text{dense}, \text{bm25}\}} \frac{1}{60 + \text{rank}_m(d)}$$
4. **Фільтри за метаданими:** Можливість миттєвого обмеження пошуку за типом документа (`doc_type`: standard / regulation / policy / technical_guide) та датою чинності.
5. **Reranking:** Переоцінка релевантності за семантичною щільністю термів та точним збігом сутностей.

### 📊 Результати бенчмарку якості пошуку (15 контрольних запитів)

Тестовий набір запитів `evals/retrieval_testset.json` охоплює всі 35 документів корпусу з розміченими еталонними чанками (Ground Truth):

| :--- | :---: | :---: | :---: | :---: | :---: |
| **1. Тільки Dense (Vector)** | **100.0%** | **100.0%** | **100.0%** | **1.000** | **0.4 ms** |
| **2. Hybrid (BM25 + Dense RRF)** | **80.0%** | **100.0%** | **100.0%** | **0.889** | **0.6 ms** |

## 📚 RAG з джерелами та контролем контексту (Крок 3)

RAG-пайплайн (`src/rag_pipeline.py`) реалізує принцип закритого контексту з гарантією цитування та захистом від галюцинацій:
1. **Контроль бюджету токенів (Token Budget):**
   * Встановлено ліміт контексту (за замовчуванням 2000 токенів).
   * Модуль `ContextBuilder` жадібно упаковує знайдені чанки за спаданням релевантності. Якщо наступний чанк перевищує залишок бюджету, він безпечно відсікається без ризику переповнення контекстного вікна.
2. **Обов'язкове цитування [Документ, Розділ]:**
   * Кожне окреме фактологічне твердження моделі супроводжується точним посиланням у тексті:
     `[Назва документа, Розділ]`.
   * Наприкінці відповіді формується підсумковий структурований блок `Джерела:`.
3. **Детермінована відмова «Не знаю»:**
   * Якщо релевантних чанків немає або знайдений контекст не містить прямої відповіді на запитання (unanswerable запити), модель не вигадує правдоподібні пояснення, а повертає строго стандартизовану фразу:
     `У наданих документах немає цієї інформації.`
4. **Версіонування системних промптів:**
   * `prompts/rag_v1.txt` — базовий RAG-промпт.
   * `prompts/rag_v2.txt` — покращений промпт із суворим принципом закритого світу (Closed-World Assumption) та жорсткою відмовою.
   * `prompts/CHANGELOG.md` — обґрунтування змін та емпіричних покращень.

## 🧪 Тестсет, Калібрування LLM-as-a-Judge та Evals у CI (Крок 4)

Для автоматизованої перевірки якості RAG-системи у CI реалізовано повноцінний eval-пайплайн:
1. **Тестовий набір (Testset $\ge$ 20 запитань):**
   * Файл `evals/testset.json` містить **22 запитання**:
     - 13 фактологічних запитань з різною структурою відповідей;
     - 5 запитань без відповіді в корпусі (unanswerable) для перевірки відмови «Не знаю»;
     - 4 запитання-пастки (adversarial traps) з застарілими версіями регламентів (2018, 2019) та суміжними поняттями.
2. **Scoring-функції:**
   * **Детерміновані:**
     - `CitationScorer`: перевірка наявності та правильності цитування первинних джерел.
     - `KeyFactsScorer`: перевірка наявності ключових нормативних фактів і числових порогів.
     - `RefusalScorer`: строга перевірка повернення «Не знаю» там, де треба, і відсутності відмов на фактологічні питання.
     - `FaithfulnessScorer`: оцінка заземлення тверджень у наданому контексті (відсутність галюцинацій та вигаданих джерел/чисел).
   * **LLM-as-a-Judge з калібруванням:**
     - Модуль `evals/judge.py` порівнює відповідь системи з еталонною (Ground Truth).
     - Суддя попередньо відкалібрований на 10 зразках ручної розмітки (`evals/calibration_sample.json`): **Pearson $r = 0.887$**, **MAE = 0.14**, **Agreement Rate = 60.0%**.
3. **CI Quality Gates (GitHub Actions):**
   * Пайплайн у `.github/workflows/ci.yml` автоматично запускається на кожен push/pull request.
   * Визначає критичні пороги якості (Quality Gates), нижче яких збірка падає:
     - `Citation Accuracy >= 80.0%`
     - `Refusal Accuracy >= 90.0%`
     - `Faithfulness >= 80.0%`
     - `Overall Score >= 80.0%`
